# Hatch — Tailor prompts & skills review (CV/CL quality fix)

> **For Claude Code:** Implement in priority order (P0 → P1 → P2). Use the project TDD loop: write the failing test, implement, run green, commit. File paths and exact edits are given. Do **not** restyle working code; this is a correctness job.

**Date:** 8 June 2026
**Repo:** `arvindsoni2/hatch`
**Trigger:** `cv_v1_A.docx` + `cl_v1_A.docx` generated by the Tailor agent (Ollama `gemma3:e2b`) for *Enterprise Architect (Business Systems), Mace* contained leaked placeholders, a missing company name, LaTeX currency artefacts, broken skill labels, and weak sector alignment.

---

## 0. Why prompt edits alone will not fix this

The bad output is produced by **four independent failures stacked on top of each other**. Fixing only the `.j2` prompts changes nothing for three of the four. Address them in this order:

| Layer | Failure | Fixed by |
|---|---|---|
| **Plumbing** | JD-analysis prompt keys don't match the Pydantic schema → company name, rate, contract type, sector signals silently dropped | Task 1 |
| **Plumbing** | `SKILL.md` instructions are never injected into the CV/CL/ATS generation prompts — the skills are dead documentation | Task 2 |
| **Data** | The user's `master_cv.json` is an unfilled template (`PLACEHOLDER – Company A`, `your.email@domain.com`, `$\textsterling`) and nothing validates it before tailoring | Tasks 3–4 |
| **Model** | `gemma3:e2b` (~2B) cannot reliably satisfy strict nested-JSON + word-count + multi-paragraph constraints | Task 5 |
| **Prompts** | Prompts permit bracketed placeholders, don't ground on company/sector, don't bridge transferable sector experience | Tasks 6–9 |

## P0 — Plumbing (do first; highest impact, model-independent)

### Task 1 — Align `jd_analysis.j2` keys with the Pydantic schema

The prompt and `schemas/tailor.py` have diverged on **six** fields. Pydantic ignores unknown keys, so the model's correct extractions are thrown away. This is the single largest cause of poor grounding.

**Confirmed mismatches** (prompt key → required schema field):
- `company_context.name` → **`company_name`**
- `company_context.size_signals` → **`size`**
- `company_context.culture_signals` → **`culture_indicators`**
- `contract_details.rate` → **`rate_range`**
- `contract_details.type` → **no field exists** (add `contract_type` to `ContractDetails`, or drop from prompt)
- `requirements.education` → **no field exists** (add `education: str | None = None` to `Requirements`, or drop from prompt)

**Files:** `backend/app/prompts/jd_analysis.j2`, `backend/app/schemas/tailor.py`

- [ ] **Step 1 (test, red):** add `backend/tests/test_services/test_jd_analysis_schema.py` that feeds a fixed JSON blob using the prompt's documented keys into `JDAnalysisResult.model_validate(...)` and asserts `company_context.company_name == "Mace"`, `contract_details.rate_range` and `company_context.sector` are populated. It will fail (keys dropped).
- [ ] **Step 2:** Make prompt and schema agree. Preferred fix = **edit the prompt JSON schema** to use the real field names (`company_name`, `rate_range`, `size`, `culture_indicators`) and either add `contract_type`/`education` to the schema or remove them from the prompt. Add an explicit instruction near `company_name`:
  > `"company_name"`: the hiring organisation's name exactly as written in the JD (e.g. "Mace"). If genuinely absent, use `null` — never a placeholder.
- [ ] **Step 3:** Run green. **Commit:** `fix(jd-analysis): align prompt keys with JDAnalysis schema so company/rate/sector survive parsing`

### Task 2 — Inject `SKILL.md` instructions into the generation prompts

`services/cv_tailor.py` calls only `render_prompt(...)`. `CvTailoringSkill.instructions()` / `CoverLetterSkill.instructions()` (the SKILL.md bodies) are never used. Make the skills real.

**Files:** `backend/app/prompts/cv_tailoring.j2`, `cl_generation.j2`, `ats_keywords.j2`; `services/cv_tailor.py`, the cover-letter service, the ATS service; `skills/wrappers.py`.

- [ ] **Step 1 (test, red):** assert that the rendered CV prompt contains a distinctive sentence from `cv-tailoring/SKILL.md` (e.g. "flag it as a gap rather than inserting it") when the skill loader is available.
- [ ] **Step 2:** add an optional `skill_instructions: str = ""` variable to each generation prompt, rendered in a `## SKILL GUIDANCE` block when present. In each service, load `SkillLoader(...).instructions("cv-tailoring" | "cover-letter" | "ats-optimization")` and pass it into `render_prompt`. Keep it defensive: empty string when the skill is missing (loader already returns `""`).
- [ ] **Step 3:** green. **Commit:** `feat(skills): inject SKILL.md guidance into CV/CL/ATS generation prompts`

### Task 3 — Pre-flight master-CV validation gate + normalisation

Block tailoring when the master CV is an unfilled template, and strip markup on the way in.

**Files:** `backend/app/services/cv_tailor.py` (or a new `services/master_cv_validator.py`), `services/resume_store.py` (ingest).

- [ ] **Step 1 (test, red):** `test_master_cv_validator.py` — a master CV containing any of `PLACEHOLDER`, `XXXX`, `your.email@domain`, `[`...`]`, or `\textsterling` raises/returns a blocking validation error listing the offending fields.
- [ ] **Step 2:** implement `validate_master_cv(cv: dict) -> list[str]` that scans personal block, summary, experience headers, and achievements for: placeholder tokens (`PLACEHOLDER`, `XXXX`, `TODO`, `[…]`, `your.email`, `your-profile`), and LaTeX/markup artefacts (`\textsterling`, `$…$`, `\&`). Call it at the **start** of `CVTailor.tailor()`; if blocking issues exist, raise a typed error the router surfaces to the UI ("Complete your master CV before tailoring: …").
- [ ] **Step 3:** add `normalise_master_cv(cv)` that replaces `\textsterling`→`£`, strips `$…$` wrappers, collapses `\&`→`&`, and trims stray markdown bold (`**`). Run it on resume ingest **and** as a safety net before tailoring.
- [ ] **Step 4:** green. **Commit:** `feat(tailor): block tailoring on unfilled master CV; normalise LaTeX/markup artefacts`

### Task 4 — Make the fabrication/placeholder validator block, broaden its scope, surface it

`_validate_no_fabrication` only fuzzy-checks achievement bullets, only logs, and never inspects the summary, skills, certifications, or for placeholders.

**Files:** `backend/app/services/cv_tailor.py`, `routers/tailor.py`, frontend tailor result view.

- [ ] **Step 1 (test, red):** a tailored result whose `summary` contains `[Company Name]` or whose any field contains a placeholder token produces a **blocking** warning, not just a log line; and a fabricated achievement (no master match) is flagged.
- [ ] **Step 2:** extend the validator to (a) scan `summary`, `skills[].items`, `certifications`, and experience headers for placeholder tokens (reuse Task 3's token list); (b) keep the fuzzy achievement check but raise the floor and include the summary; (c) return a structured result `{blocking: [...], advisory: [...]}`. Surface `blocking` in the API response and render it in the Review gate so the user sees *why* a document was withheld.
- [ ] **Step 3:** green. **Commit:** `fix(tailor): broaden fabrication/placeholder validation and surface blocking issues to the Review gate`

### Task 5 — Route document generation to the primary model, not the triage model

`gemma3:e2b` is a ~2B-class model; the CV/CL/ATS prompts require strict nested JSON, exact word counts and 4-paragraph structure. This is beyond its reliable instruction-following and explains the schema drift and placeholder leakage.

**Files:** `backend/app/services/cv_tailor.py`, cover-letter service, ATS service, `agents/tools/llm_factory.py`, `examples/profile_*.yaml`, docs.

- [ ] **Step 1:** ensure CV tailoring, cover-letter generation, and summary rewrite call **`get_primary_model()`**, while JD keyword extraction / triage may stay on `get_triage_model()`. Verify they aren't all defaulting to the same small Ollama model.
- [ ] **Step 2:** update the docs / example profiles to recommend a capable primary model for document generation (e.g. the Qwen3-14B llama.cpp path already specced in `2026-06-02-async-llm-latency-design.md`, or a hosted model), and note that `gemma3:e2b` is triage-only. Add a soft warning in `llm_factory` when the configured primary model is a known-small model.
- [ ] **Step 3:** **Commit:** `fix(llm): generate CV/CL on primary model; restrict gemma:e2b to triage; document model tiers`

## P1 — Prompt hardening (per file)

### Task 6 — `cv_tailoring.j2`

- [ ] Add an explicit **placeholder ban** to CRITICAL RULES:
  > Never emit bracketed placeholders (`[Company Name]`, `XXXX`, `your.email`). If a value is unknown, omit the clause — do not invent a placeholder. Never reproduce LaTeX/markup tokens (`\textsterling`, `$…$`); write `£` for GBP.
- [ ] Add **explicit grounding variables**, don't rely on the model digging them out of the JSON blob. Pass `target_company`, `target_sector`, and `top_requirements` as first-class template vars and reference them in the instructions ("Rewrite the summary to lead with relevance to **{{ target_sector }}** at **{{ target_company }}**").
- [ ] Add **sector-transfer guidance** (this directly fixes the energy/aviation/finance → construction gap):
  > When the candidate's sectors differ from the target sector, do not claim target-sector experience. Instead, surface the *transferable* proof points (regulated-industry delivery, large programme governance, data-platform consolidation) and frame them in the target sector's language.
- [ ] Fix the **empty skill category** problem: give 3–4 concrete category names in the schema comment (e.g. "Cloud & Infrastructure", "Data & AI", "Architecture & Design", "Delivery & Leadership") and instruct: every `category` must be a non-empty display label.
- [ ] **Small-model robustness:** move the JSON schema to the very end, lead with a one-line task statement, and convert the rule list into short imperative bullets. Consider a tiny worked example of one tailored bullet.

### Task 7 — `cl_generation.j2` + `docx_cl_builder.py`

- [ ] Pass `company_name` and `sector` as explicit template variables (sourced from the now-correctly-parsed JD analysis). Instruction:
  > Use `{{ company_name }}` verbatim in paragraph 1. If `{{ company_name }}` is empty, open with the role and sector instead — never write "[Company Name]" or "the Company".
- [ ] Add the same placeholder/LaTeX ban as Task 6.
- [ ] In `docx_cl_builder.py:95`, keep `"the Company"` only as a last-resort, but the upstream fix (Task 1) should make it rare; add a test that a populated `company_name` reaches the docx payload.

### Task 8 — `summary_rewrite.j2`

- [ ] Add sector-transfer guidance and the placeholder ban (mirror Task 6). Ensure it receives `target_sector`/`target_company`.

### Task 9 — `ats_keywords.j2`

- [ ] Minor: instruct that `missing_critical` must be a subset of the JD must-haves, and that suggestions must reference real master-CV content (no "add X" where X isn't in the master CV — that would invite fabrication). Wire `instructions()` from `ats-optimization/SKILL.md` (Task 2).

### Task 10 — CV docx builder fixes

- [ ] **Skill label:** when `category` is empty/whitespace, render the items **without** the `:` prefix (don't print `**:  **`).
- [ ] **Footer:** populate the `X of Y` page field (or remove the literal). Confirm in `generate_cv_docx.js` that the page/numpages fields are set; add a render test asserting the footer has no dangling "of".

## Data hygiene (user action, document in README/onboarding)

The leaked `PLACEHOLDER`, `XXXX`, `your.email@domain.com`, and `$\textsterling` originate in the **user's `master_cv.json`**, which is an unfilled, LaTeX-converted template. Tasks 3–4 make the system refuse to ship such output, but the master CV must still be completed. Ensure the onboarding/resume-upload flow either parses a real CV into `master_cv.json` or walks the user through filling every field — and runs `normalise_master_cv` on save.
