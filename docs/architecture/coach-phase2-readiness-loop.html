Interview Readiness Loop

Phase 1 records and evaluates practice. Phase 2 turns that evidence into a one-page brief before each real interview, and learns back from a two-minute debrief afterwards. Everything works with AI switched off; local models only add short wording.

This page illustrates the specification 2026-10-22-coach-phase2-readiness-loop.md. Where they differ, the Markdown spec wins.

Principles

spec §4
  • Deterministic skeleton, model garnishEvery feature is complete without a model. Models only rewrite supplied content into short text.
  • Derive, don't storePatterns are computed on read. Only user decisions, user-authored content and cached model text are stored.
  • Separate evidence kindsPractice levels, real-interview self-ratings and story coverage are never merged into one score.
  • Calibrated approvalObservations appear immediately and can be dismissed. Writes into Question Bank or Stories need explicit acceptance.
  • CPU-first budgetsOutputs ≤ 600 tokens, thinking off, deadlines measured on the owner's laptop including queue time.
  • No new infrastructureSame FastAPI, SQLite, runtime and llama.cpp image. No owner key; Phase 1 has none.

Architecture

spec §5

A new services/coach_readiness/ package owns the logic and routers/coach_readiness.py serves every Phase 2 route. It reads existing domains through their public seams and calls models only through the shared runtime. Existing domains never import it: they report edits and deletions through the neutral services/source_events.py hook, whose listener is registered at start-up.

Status models

spec §8

These are the only legal statuses. Any transition not drawn returns invalid_state (409).

Pattern derived, not stored

stateDiagram-v2
  [*] --> forming: 1 session
  forming --> focus: 2 weak
  forming --> strength: 2 strong
  forming --> mixed: one of each
  focus --> mixed
  strength --> mixed
  mixed --> focus: latest 3 weak
  mixed --> strength: latest 3 strong
  focus --> stale: newest of latest 3 over 90 days
  strength --> stale
  mixed --> stale
  stale --> mixed: fresh session

Dismissed is an overlay stored as a fingerprint. New evidence changes the fingerprint and the pattern reappears. Trends are labelled against difficulty: Improving or Changed at an easier difficulty; Getting weaker or Lower at a harder difficulty.

Focus area stored

stateDiagram-v2
  [*] --> active: create, takes slot 1-3
  active --> paused
  paused --> active
  active --> achieved: candidate marks
  achieved --> active: reopen
  active --> archived
  paused --> archived

Achieved is suggested when every criterion is met, but only the candidate sets it.

Practice plan stored

stateDiagram-v2
  [*] --> draft
  draft --> active: Start
  draft --> discarded
  active --> completed: all items done or skipped
  active --> superseded: another plan started
  active --> expired: 14 days or round passed

Items: todo → done or skipped. Practice-session items tick themselves when a matching session completes.

Brief skeleton always fresh; row tracks tips

stateDiagram-v2
  [*] --> active: round scheduled
  state active {
    [*] --> none
    none --> enhancing: opened or scheduler
    enhancing --> current: grounding passes
    enhancing --> unavailable: failed or fenced
    unavailable --> enhancing: Try again
    current --> outdated: fingerprint changed
    outdated --> enhancing: re-queued
  }
  active --> archived: over, completed or cancelled

UI: Ready · Adding tips · Ready, tips added · Tips out of date · Tips unavailable · Archived. No Refresh button.

Debrief stored, user-authored

stateDiagram-v2
  [*] --> due: round completed or time passed
  due --> draft
  due --> skipped
  skipped --> draft: later
  draft --> saved
  saved --> saved: edit

Cancelled rounds never make a debrief due; a debrief already saved is kept. Saved debriefs carry proposals (add to Question Bank, record story use) that are accepted or dismissed one by one.

Model generation per request

stateDiagram-v2
  [*] --> queued: dedupe by fingerprint
  queued --> running
  running --> validating
  validating --> succeeded
  validating --> repairing: first failure
  repairing --> validating
  validating --> degraded: second failure
  running --> degraded: deadline
  running --> fenced: source re-check fails

Local model qualification catalogue status + bench report

stateDiagram-v2

  candidate --> benching
  benching --> qualified: tier gate passed twice
  benching --> rejected
  qualified --> promoted: route regression bench passes too

Local model tiers

spec §9

Candidates are benched on synthetic Coach fixtures. Tiers T and S share the existing routes, so a model is promoted only if it passes the Phase 2 gate and the route's existing regression bench (Phase 1 acceptance-smoke for S, job-scoring triage checks for T). Only promoted models enter model_tiers.json. If none pass, the current model stays.
